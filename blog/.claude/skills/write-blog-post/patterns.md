# 構成パターン集

ブログ記事を書く際に使う「構成の型」集。パターンごとに再利用可能な見出し構成と、埋める観点をまとめる。育てる前提で作るので、新しい型が固まったらここに追記していく。

SKILL.mdの「3. 構成を検討する」で候補を挙げるとき、ここにある型も選択肢に含める。

## 経験談型(壁 → 転換点 → 教訓)

課題に直面した経験を、転換点を挟んで教訓に昇華させる型。読者は「自分も同じ壁にぶつかったときにどうすればいいか」を持ち帰る。

### 向いているトピック

- 単調だがパターン・対応範囲が広いタスク(例: 多数のリポジトリへのセキュリティ対策)に対してAIワークフローを設計している、など具体的な失敗・気づきの経験がある場合
- 「良かれと思ってやったことが裏目に出た→やり方を変えたらうまくいった」という起伏がある経験

### 見出し構成

1. **導入**: 何に直面していたか(タスクの性質、目指していたゴール)
2. **何があった**: ぶつかった壁を具体的に(複数ある場合は箇条書き)。抽象的な議論に沈んでしまった経緯があれば含める
3. **転換点**: 何がきっかけで方針を変えたか
4. **結果**: 転換後に何が起きたか、具体的な変化
5. **そこから得たこと**: 一般化した教訓 + (必要なら)気負わなくていいという後押し

### 書くときのコツ

- 本文に入る前に「伝えたいこと」を「誰向けか」「結論」の2点だけに絞る。構成の相談はそのあと
- 壁は抽象的な失敗談で終わらせず、「実際に何をして、何が起きなかったか」まで書く
- 転換点は「やめたこと」とセットで書くと効く(例: 抽象的に考えるのをやめて、具体タスクを1件回した)
- 教訓は具体エピソードから一般化した1文に絞る。欲張って複数の教訓を詰め込まない
- タイトルは結論を要約するより、読者の心の声(「え、そんなの自分がやるの!?」のような)を拾うと刺さりやすい

### 実例

- 260916_workflow_first_lap.md(仮): 200リポジトリ規模のセキュリティ対策ワークフロー設計で、抽象的な改善に沈んで手が止まった話
